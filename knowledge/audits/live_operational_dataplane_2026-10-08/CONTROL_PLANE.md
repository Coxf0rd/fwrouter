Baseline source: `6ba7f6f` (worktree clean at inspection). Host-local date: 2026-10-08 +07; corresponding raw UTC timestamps are on 2026-10-07. This file records bounded live measurements, source-traced lifecycle semantics, and root-authorized test-client operations. ## Read-only live measurements

`CONTROL_READS_RAW.json` is the exact raw measurement record. `scripts/read_only_control_plane.py` issues six serial GET classes, five repetitions each, to loopback API port 5000. It drains each response to count bytes and discards the body; no response payload, job data, identities, or settings values are persisted. It performs no external provider call by design of the selected routes. A 60-sample cgroup counter snapshot calibration measured p50 48.0 μs and max 122.7 μs; this is observer call cost, not sampler-derived API CPU. Requests are timed end-to-end by monotonic clock, with no per-request resource sampling. The resource window surrounds the full 30-GET cohort; it includes natural concurrent/background activity and cannot be attributed to requests.

## Xray external-client lifecycle contract traced at baseline

Source routes are mounted under `/api/v2`:

| Operation | Endpoint | Behavior / terminal proof |
|---|---|---|
| list clients | `GET /xray/clients` | service inventory read; response includes sensitive client identity fields, so benchmark captures must discard body |
| create | `POST /xray/clients` | accepted `xray_client_create` job; worker modifies Xray inbound, native-tests candidate, reloads Xray, syncs local inventory, materializes bindings/profile when applicable, then verifies effective runtime contains client before job reports success |
| alias edit | `PATCH /xray/clients/{client_id}` | synchronous FWRouter metadata change; adapter `update_client_alias` returns metadata-only success and does not reload Xray; local alias persistence and audit event follow |
| delete | `DELETE /xray/clients/{client_id}` | accepted `xray_client_delete` job; worker removes Xray client, native-tests/reloads config, syncs inventory, clears only that client's scoped projections/overrides, materializes bindings, then verifies effective runtime absence before job success |
| subject mode | `POST /subjects/{subject_id}/mode` | apply job; mode supports Disabled for explicit client subject, but is a separate operation after create and cannot close the initial enabled window |
| fixed route | `POST /subjects/{subject_id}/server-override` | shared apply job with server ID and actor scope; changes subject route intent/runtime and is not part of client CRUD |
| clear fixed route | `DELETE /subjects/{subject_id}/server-override` | shared apply job; clears subject route intent/runtime |

`POST /xray/clients` accepts `alias`, optional `email`, optional `requested_by`, and `allow_blocked_egress` (default false). It has no disabled-at-create flag and no caller UUID. Omitting email generates a unique UUID internally and derives a default client email from alias/UUID; it avoids the optional email-token subscription-profile branch. The create worker still creates an enabled Xray inbound identity. Its subscription URI/UUID is usable access material. The only client operations measured here use the dedicated audit identity; production identities were not created, edited, routed, disabled or deleted.

Create returns an accepted job rather than verified success: route/service start waits up to one second for job progress, after which `queued`/`running` remains HTTP success. Only terminal `success` plus `runtime_verified=true` from the job result is the source-level verified convergence claim. HTTP success at submission must not be recorded as effective or verified latency. Delete has the same accepted-job boundary. Successful delete performs exact client deletion and scoped cleanup; a missing runtime client can invoke local tombstone cleanup if matching local subject state remains, so retries must use only the captured exact ID and inspect current inventory first. Create has an identity lock derived from alias/email; delete has a per-ID lock. These are duplicate admission controls, not durable idempotency receipts for successful requests.

## One live Xray client create

Root authorized exactly one no-email test-client create. Preconditions passed: protected DB/config backup existed; no active jobs; Xray forced VPN and egress were already ready; 78 existing identities/bindings were captured. One `POST /xray/clients` used `allow_blocked_egress=false` and `requested_by=operational_live_audit`; it returned HTTP 200 in 1112.782 ms with an accepted job. It did not mean convergence: terminal `success` with `runtime_verified=true` was observed 23,642.365 ms after request start (22,529.307 ms after accepted observation). The job was polled 40 times; polling consumed 3022.693 ms in aggregate, with a 719.120 ms maximum request. These GETs add observer load and are not subtracted from the service interval.

Readback found exactly one test client, 79/79 bindings applied and verified, `forced_vpn_ready=true`, and no pending generation. All 78 existing identities and their binding semantics matched. The independent semantic review confirmed unchanged preexisting per-user routes, non-user route rules, all 15 preexisting outbounds, global routing fields, ordering and handoff mappings; only the test identity, its scoped route rule and its binding were added. Volatile applied/verified timestamps and aggregate counts were excluded from the semantic comparison. The generated identity was held in a mode-0600 private file for the authorized probe and exact cleanup; cleanup later removed the file. This document contains no UUID, email, or subscription URI.

Docker events prove two actual Xray runtime restart cycles during this one create workflow. Both sent SIGTERM (15); cycle 1 kill-to-die was 196.352 ms and die-to-start 274.280 ms (470.631 ms total); cycle 2 was 170.081 ms, 241.371 ms (411.452 ms total). Two short-lived Xray candidate-test containers each took about 475–490 ms from create through destroy. The first runtime start completed at 1.056 s; the second candidate container was not created until 21.297 s, leaving about 20.24 s between restart completion and second candidate creation. Thus restart duration does not explain the 23.6 s terminal latency. Source tracing places configuration validation/reload and binding materialization/apply on this common workflow, but the exact internal stage responsible for that 20.24 s gap and its CPU share were not directly instrumented. Do not attribute the gap to a particular stage without further spans. Existing Xray client streams may be interrupted by these restarts.

Resource numbers are bounded co-interval observations, not pure action attribution: 233 target-100ms samples covered request, polling and readback plus background activity. API subtree CPU increased 27,114,476 μs; sampled API `memory.current` peak was 577,798,144 B (start 471,699,456 B, end 527,269,888 B); API subtree write I/O increased 22,282,240 B / 1,869 write operations. This includes 40 polling GETs and child/background work. Raw interval rows were not retained, so CPU peak-per-interval is unavailable. Sampler call wall cost was p50 0.819 ms, max 25.847 ms. Xray process RSS sampled peak was 41,762,816 B, but transient processes may be missed; process CPU and Xray cgroup CPU/I/O are unavailable across the runtime/cgroup incarnation change. Mihomo stable-cgroup CPU increased 1,490,541 μs and sampled RSS peak was 149,819,392 B over the same co-interval, so it is background context only. Negative Xray cgroup I/O counter differences are invalid across incarnation and are recorded as unavailable in the corrected raw evidence.

The test client had one alias edit, one fixed-route apply, and one exact-ID delete. The fixed-route apply's result is recovered below because its measurement harness failed after the operation, before persisting timings/resources. The test client was then deleted successfully and all preexisting client/binding semantics matched. Enable/disable, a second client and batch lifecycle remain unmeasured/staging-only. Alias edit is source-traced as metadata-only with no native reload. Batch create/delete is staging-only given the observed two restarts and roughly 23.6 s convergence for one client.

## Same-value settings, policy, log and alias operations

Three serial `PUT /ui/settings/display` calls replayed the current non-secret display settings without changing the effective value. Response latencies were 5.234, 4.259 and 3.933 ms (p50 4.259 ms; n=3 tail is not stable). A single policy-only `POST /subscription/sources/{source_ref}/provider/configuration` with `allow_automatic_member_switch=false` returned HTTP 200 in 8.184 ms; readback stayed false at binding revision 4. These are same-value save paths only, not measurements of changed setting/policy propagation. API-only evidence is in `NOOP_CONTROL_RAW.json`; it has no request-level CPU or DB instrumentation.

The existing `write_operational_log` function created one record then a serial burst of ten, all with event IDs and no deduplication. The single call took 20.398 ms; the ten-call phase took 49.599 ms total (3.623–6.126 ms per call). SQLite's trace callback observed exactly 11 INSERTs, 11 BEGINs and 11 COMMITs, with zero SELECT/UPDATE/DELETE statements from this writer path. Process CPU for the whole subprocess was 36.266 ms; `/proc/self/io` `write_bytes` increased 884,736 B (kernel-accounted process writes, not SSD/physical-media proof), while logical write bytes (`wchar`) increased 429,224 B. RSS is boundary-only (36.36 MB → 37.63 MB). The 11 audit log rows and JSONL events are intentionally retained; no cleanup was run. See `LOG_CREATE_RAW.json` (private mode 0600).

One exact-test-client alias PATCH returned HTTP 200 in 16.430 ms; exact-identity GET readback took 4.826 ms and matched the new alias. Source path is synchronous metadata-only. No runtime restart was intended; the current evidence has no Docker event bracket specifically around this PATCH, so runtime no-reload is source-traced, not separately event-confirmed. No secret identity value is recorded; see `XRAY_ALIAS_EDIT_RAW.json`.

## Fixed route, exact cleanup, deploy and API restart

One approved `POST /subjects/{test_subject_id}/server-override` targeted an already-applied fixed server, with the scope limited to the dedicated audit client. It completed as a successful apply job. The measurement harness raised `KeyError: wall_ns` after terminal/readback collection while formatting sampler results, so request latency, accepted-to-terminal latency, and resource values were not persisted; the POST was not retried. `XRAY_FIXED_ROUTE_RECOVERY.json` records read-only recovery: target readback matched, Xray was running and forced-VPN-ready, 79/79 bindings were applied and verified, and no generation was pending. The 78 preexisting client records, binding rows, and per-user/non-user routing semantics matched; global mode/auto target, provider member/revision and policy remained unchanged. Docker history for the bounded operation shows one candidate validation container and one Xray runtime restart with SIGTERM 15. The API's `runtime_state_unchanged=true` result flag is not evidence that no native action occurred. The single public TLS/WSS fixed-route data probe did not run: the data harness failed its readiness check on an unused raw listener before issuing any GET; root prohibited retry. This traffic case is unmeasured.

The exact test-client DELETE returned HTTP 200 in 1124.724 ms. Terminal success with `runtime_verified=true` was observed 21,121.647 ms after request start (19,996.600 ms after accepted observation); 36 polls consumed 2490.417 ms. Readback proved the test identity and subject absent, all 78 original identities and binding rows restored, non-test routing semantics equivalent, global route state unchanged, and Xray running/forced-VPN-ready with 78/78 bindings verified and no pending generation. A terminal race briefly showed one running job in the immediate readback; a fresh DB read at 18:44:50.596 UTC showed zero active jobs and unchanged provider member 1456, binding revision 4, policy false, and auto-selection revision hash. Cleanup gates passed and the private identity file was removed. Docker events show two Xray restart cycles, each SIGTERM 15, and two candidate containers during delete. The container identity remained the same and restart count remained zero, while its start time advanced. Resource co-interval: API cgroup CPU +24,044,121 μs across 220 samples, sampled `memory.current` peak 594,161,664 B, process RSS (API) is not separately available in this record; API I/O +23,838,720 write bytes / 2147 write operations. The 36 job-poll GETs and background work are included. Xray RSS sampled peak 41,213,952 B; Xray cgroup CPU/I/O unavailable across incarnation change; its cgroup memory was present for only 0–1 samples. Sampler overhead p50 0.799 ms, max 29.393 ms. See `XRAY_DELETE_RAW.json` (private mode 0600).

After exact cleanup and zero-active-job verification, one `installer/install.sh --deploy --component backend` completed with return code 0 in 64.115 ms. The deploy itself did not restart the API. Critical readiness (health, Xray, selector and routing HTTP 200 plus state readback) passed 293.463 ms after deploy command start; Xray remained running, forced-VPN-ready, and 78/78 verified with no pending generation. One `systemctl restart fwrouter-api.service` then returned 0 in 365.104 ms, but critical HTTP readiness took 44,613.753 ms from restart start. Journal evidence records successful prior shutdown, new process PID startup and “Application startup complete”/Uvicorn listening at approximately 18:48:42 +07. The delay occurred during application startup after process launch; this benchmark did not isolate a more specific stage. The one-shot marker was written at `/run/fwrouter-v2/live-bench-xray/api-restart-begin` immediately before restart, but systemd's `RuntimeDirectory=fwrouter-v2` cleanup removed it during stop. The data watcher therefore missed the marker and took no restart-window probes; this is an observer/marker lifecycle defect, not a dataplane result. No replacement probes or restart were run.

API restart resource observer captured 444 numeric samples at nominal 100 ms. Whole-window API cgroup CPU and I/O deltas are unavailable because the counter reset at restart; do not bridge old and new incarnations. Largest adjacent valid cgroup CPU interval was 342,520 μs over 100.98 ms. Sampled API cgroup `memory.current` peak was 551,124,992 B; MainPID RSS sampled peak was 503,762,944 B across the two PID epochs (not a single-process continuous peak). Sampler call wall cost p50 0.315 ms, max 35.318 ms; 1-second `systemctl show` sampling is observer overhead. The API restart co-interval includes startup, readiness polls, background activity and sampler cost, not pure restart CPU. Pre-restart endpoint CPU/I/O/resource values for the old PID were not captured, so no whole-mutation-window resource delta is available. Before/after provider bracket in this operation was unchanged: current/applied member 1456, binding/applied revision 4, automatic member switch false, same auto-selection revision hash. The separate post-restart provider metrics bracket reports zero changes within the final post-restart observation window. Final state readback shows schema 24 healthy, Xray running, 78/78 bindings, zero active jobs, and no failed systemd units. `FINAL_STATE.json`, `API_DEPLOY_RESTART_RAW.json`, and `PROVIDER_POST_RESTART_BRACKET.json` hold the receipts.

## Classification

- Measured live: six read-only API GET classes above, n=5 each; one test-client create and one exact delete through terminal verified convergence; alias edit; one dedicated-client fixed-route apply (terminal/readback and runtime events, but no saved timing/resource sample); three same-value Settings saves; one same-false provider policy save; one plus ten real audit log creates with exact writer SQL counts; backend-only deploy/readiness; one API restart/readiness; Xray runtime restart cycles observed during create, fixed-route apply and delete; exact semantic preservation/restoration of all 78 preexisting identities/bindings.
- Measured partially: API cgroup CPU/memory/I/O co-interval, Xray/Mihomo sampled RSS, stable Mihomo cgroup CPU; delete and restart resource captures; all overlap background and observer traffic as described above. API DB statement counts, WAL/fsync, and action-only CPU are not observed.
- Unsafe/staging-only: create-time disabled client, shared/global route or mode switch, provider policy enablement, mutation batch, general reset/retention cleanup paths, forced restart/outage, Mihomo restart/reload, and Auto membership toggle.
- Unmeasured: fixed-route public TLS/WSS data request (readiness harness failed before any GET); restart-window data-plane overlap (marker was removed by systemd runtime-directory cleanup); global VPN-auto and ordinary/manual server switch mutations; Direct↔VPN control-plane transition; subscription changed/no-op refresh; reconcile; Auto membership toggle; provider policy enablement; job/event lifecycle beyond observed create/delete job receipts; DB transaction counts for API operations, WAL/fsync attribution, provider-call attribution during mutations, direct handler CPU, CPU interval peak for create, and complete pre-restart-to-post-restart resource delta. Xray/Mihomo/API extra restart/reload variants were not repeated.

The Xray subscription gateway unit was active at the earlier observation and the final systemd failed-unit list was empty. A gateway-specific restart count was not retained, so it is unmeasured. No optimization or roadmap change is justified by these bounded measurements. This file and its raw receipts are evidence only.
