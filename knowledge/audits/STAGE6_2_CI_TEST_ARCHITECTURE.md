## 3. Host qualification feasibility and binding disposition

**Conclusion:** a disposable guest under a standard GitHub-hosted VM is a credible implementation path, but FWRouter host qualification is **NOT VERIFIED**, not infeasible by proof and not PASS. No VM/host experiment was executed in this audit. The existing non-root read-only Compose fixture drops capabilities and denies devices/host mounts/networking; it cannot be upgraded to host proof merely by relabeling its results ([CONTRACT.md](../../tests/acceptance/CONTRACT.md), [compose.yaml](../../tests/acceptance/compose.yaml)).

GitHub documents standard Linux runner VMs, passwordless sudo and different public/private resource classes; `ubuntu-slim` is a container and is unsuitable here. The standard x64 resource tables currently specify 4 CPU/16 GB or 2 CPU/8 GB with 14 GB advertised storage. These tables do not prove available disk after images or an independent recovery contour. Hardware acceleration for Android is not a general Linux KVM/nested-virtualization contract. Do not require or assume `/dev/kvm`. See [official runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) and [runner image revision guidance](https://github.com/actions/runner-images#about).

The chosen feasibility task in 6.2.2 is an opt-in, non-promotional **host-capability profile** using pinned QEMU software emulation/TCG and a digest-pinned disposable Debian guest. Keep the controller on the outer runner, outside guest systemd/network/storage. It owns QEMU process, disk overlays, isolated virtual networks, serial console and nonce; it must survive guest connectivity loss/reboot and independently terminate/inspect the guest. Never use a production/self-hosted server as fallback. KVM may be evaluated later as a separately observed accelerator, not a prerequisite silently waived.

Admission before workload execution must prove: runner class/image revision and sudo policy; verified QEMU/guest image/source; guest boot with real systemd/PID 1; clean guest reboot and controller reconnection; isolated networking without LAN bridge or production routes; sufficient measured CPU/RAM/disk headroom; bounded controller-driven cleanup even after guest unresponsiveness. Use synthetic DB/config/credentials and guest-only Docker where required. No production secrets, provider calls, host Docker socket or host device passthrough. Pins, console/journal excerpts, resource facts, reboot identity and cleanup evidence enter the existing producer/bundle contract.

First qualify capabilities only, then non-destructive guest unit/restart/admission/network smoke. Resource/runtime costs of this guest are currently **NOT MEASURED**; determine headroom and safety limits during the bounded spike, not by arbitrary test-count cuts or borrowed container timings. If a prerequisite fails, the producer is BLOCKED/INCOMPLETE with required tests NOT RUN; 6.2 host acceptance cannot be marked complete. A material infeasibility requires an owner-approved supported-platform/disposition change, not an automatic SKIP or transfer to production.

Stage 9 retains the broader supported-host/configuration/security matrix and actual deployment/physical-network acceptance. Explicitly destructive L7 remains separately acknowledged on a qualified disposable environment. Guest clean-reboot capability is not equivalent to power-loss/crash/corruption acceptance. External VPN client, real NIC/router/ISP/provider and production facts remain separately authorized live gates. No extra pre-deployment stage is introduced.

## 4. One result bundle; extend existing validators

Run qualification is **PASS / FAIL / INCOMPLETE**; timeout/cancellation/collection/upload/aggregator errors are infrastructure/job reasons, not new competing case statuses. Aggregator and producer uploads use failure-aware/always collection; fail-fast must not cancel independent required diagnostics. Contract/combination coverage remains separately visible. Merge coverage only for matching source/tool/schema/context and never combine incompatible line maps. Never shorten an existing artifact's required lifetime. Full rerun is the supported qualifying retry: same source may have a new attempt, with all required producer evidence from that attempt. GitHub partial reruns remain diagnostic/nonqualifying unless the future verifier explicitly proves an equally strict provenance model; current attempt mixing stays rejected.

GitHub v4 cannot append multiple jobs to one artifact; retain immutable per-producer handoffs and one final uploader. Use error-on-missing upload, allowlisted hidden files and verified file identity/modes where needed. The action's digest-warning behavior is not a substitute for strict verification.
