# Phase A Backend Test Audit

**Audit boundary:** static source and repository metadata at `eaecab548a9e05579fd9c27396723a155224f175` (`stage/test-architecture-ci-stabilization`). No pytest collection, test execution, application import probe, native runtime, production database, Docker daemon, systemd, host networking, provider API, deployment, or runtime state was accessed for this sub-audit. The working tree was clean at entry. This report covers `backend/tests/` and its shared backend test harness, not UI/installer/gate test suites.

## Executive summary

The backend inventory contains **120 test modules**, **1,372 collected-looking test functions** (AST excludes one `@pytest.fixture` named `test_config`), **35 parametrized test functions**, and **6,624 Python `assert` statements**. These are source counts, not pytest collection counts; parametrized runtime node expansion was deliberately not evaluated. All 120 files have entries in `tests/gates/manifest.json`. The manifest assigns a file-level default and only eight node-level overrides, so most tests in a mixed file inherit one classification even when they exercise different layers.

The strongest backend coverage is in selector/recovery state transitions, Provider adapter contracts, protocol parsing and Mihomo config generation, database migration behavior, read-model consistency, and Xray generation safety. Several tests assert exact no-call behavior, failure paths and persistence fencing. That is useful negative coverage, but many tests replace the production adapter/runner, so a passing service-level test does not establish application-to-native runtime convergence.

The principal acceptance gap remains **full application Xray lifecycle against a disposable real runtime**. The tree has broad TestClient and fake-runner Xray CRUD/generation tests and a separate native Xray API/readback test. The native test launches a narrowly configured Docker container but can silently skip if its image variable or Docker is absent; it does not drive API/Core CRUD through generation, apply, restart/crash recovery, DB persistence and exact loaded-state readback as one application flow. This corroborates the Operational Performance Fixes acceptance blocker; it does not itself prove an application defect.

The common fixture isolates most ordinary tests with a temporary `FWROUTER_STATE_DIR`, disables `.env` file loading, initializes a temporary SQLite database and replaces the standard Xray/Mihomo/dataplane adapters. This is a good default. It is **process-level test discipline, not a kernel or filesystem security boundary**: the subprocess guard wraps `subprocess.run` only, while direct `Popen`, Docker clients/commands, arbitrary filesystem writes and network sockets are not denied centrally. A previous native harness reached the default Xray writer lock before state isolation; the present pytest fixture reduces that risk when it runs first, but does not make arbitrary pre-fixture code safe. Routine tests must not be run without reviewing their imports and fixture path.

No backend tests were run, so current pass/fail status and timing are unmeasured here. Historical baseline evidence is summarized below with its actual provenance and limitations.

## Test quality findings

### Confirmed strengths

1. **Common state paths are redirected for ordinary test bodies.** `backend/tests/conftest.py:194-206` places `FWROUTER_STATE_DIR` below `tmp_path`, clears cached Settings, initializes SQLite except for explicit `no_database_autoinit`, and replaces common runtime adapters. The autouse teardown waits for the job manager and clears caches (`:224-228`). The `.env` guard at `:22-24` is set only after FWRouter imports at `:12-17`, so it does not protect import-time Settings construction (see weakness 2).
2. **Failures are not universally faked into success.** Dataplane and Mihomo replacements are explicit and return labeled fake results (`conftest.py:27-87`); focused tests can then assert service decision semantics. Provider adapter tests use captured `MockTransport` responses and assert request count, cache and credential redaction (`test_stealthsurf_provider_boundary.py:33-58`).
3. **Concurrency tests generally coordinate state with barriers/events and timeouts.** For example selector/refresh tests use explicit barriers/events; `test_vpn_auto_writer_guard.py:97-145` passes an isolated state directory to child processes and uses a ready file to synchronize the process flock test.
4. **Negative cases are substantial.** The matrix includes tests whose names and exact assertion samples cover fail-closed protocol combinations, no provider call, unchanged-state no-op behavior, CAS conflicts, malformed states and no publication before readback.
5. **No blanket baseline exemption is encoded.** Manifest policy says exact node IDs remain failures and novel/unclassified cases fail selection. The historical note explicitly says the 52 failures are not exemptions (`tests/gates/manifest.json:86`).

### Confirmed weaknesses and risks

1. **Isolation is not enforced below Python.** `_install_no_live_subprocess_guard` monkeypatches `subprocess.run` and rejects a finite set of commands involving production compose paths, service restart, or dnsmasq (`conftest.py:113-132`). It does not guard `subprocess.Popen`, direct `os.exec*`, a Docker SDK, arbitrary file writes, UNIX sockets, or network sockets. A test that opts into a bypass or calls production-facing code before fixture activation is not contained by this guard. This is a proven limitation of the guard, not proof that a current test has mutated production.
2. **Import-time Settings initialization precedes the `.env` guard.** `conftest.py:12-17` imports Xray adapter modules before `conftest.py:22-24` disables `Settings.model_config["env_file"]`. The source call chain is `xray.py` importing `xray_real`'s module-level `DEFAULT_XRAY_ADAPTER` → `RealXrayAdapter()` → `_default_xray_config_path()` → `get_settings()`; that Settings class declares `/opt/fwrouter-api/.env` in `core/config.py`. The function-scoped fixture only sets `FWROUTER_STATE_DIR` at `conftest.py:194-203`, after those imports. This is a **confirmed pre-fixture Settings construction path and potential read of production `.env`/default paths**, not evidence that a particular test execution read or disclosed a secret. It is a P0 harness issue: Phase B must establish environment and disable production `.env` before importing application modules, then prove module import does not resolve production paths.
3. **Fixture isolation is function-scoped and its worker wait is not fail-closed.** The fixture calls `get_default_job_manager().wait_for_idle()` before setting the temporary state path (`conftest.py:194-203`) and ignores its boolean result; teardown also ignores it (`:224-228`). On a clean serial run there should be no active prior test worker; if a worker survives, later DB/path lookups can cross test boundaries. This is a credible race/order risk requiring a fixture change and test, not evidence that a DB write occurred during this audit.
4. **Xray writer lock path follows Settings.** `xray_common.py:35-43` creates `<settings.paths.run_dir>/xray-writer.lock`. Tests that reach the guard after the fixture has changed and cleared Settings should use the temporary run directory; direct harness invocation before that setup can use the default `/run/fwrouter-v2`. `test_vpn_auto_writer_guard.py:97-145` explicitly isolates child processes. This explains why the earlier harness incident is a relevant threat model and why pytest fixture isolation cannot be treated as a host-level safety boundary.
5. **Native Xray test can silently skip.** `test_xray_native_readback.py:20-27` skips if `FWROUTER_XRAY_TEST_IMAGE` is absent or Docker unavailable. Manifest `required_native` linkage is declarative; this source alone does not show that every required CI gate converts that skip into a blocked gate. Phase D acceptance should force the pinned image and fail if it is not provisioned.
6. **Native Mihomo environment is implicit and brittle.** `test_protocol_native_validation.py:19-22,32-47` defaults to `/tmp/fwrouter-mihomo-v1.19.31/mihomo` and asserts it exists/version matches. Without a provisioning contract, local and hosted results may differ. Its per-profile test does exercise parser → normalized source → generated candidate → native `-t`; it does not perform routing or handshake.
7. **Manifest precision is file-oriented.** All 120 backend test modules are present, but one file default level/domain is applied to all contained tests except eight overrides. AST inventory shows broad mixed modules, notably `test_xray.py` (114 tests) and `test_watchdog.py` (69), combining pure unit, TestClient, fake runtime and generation/recovery work. This can make affected selection run too much or understate scenario requirements; split metadata or overrides should follow the Phase A audit, not a blanket file rename.
8. **Durations are not measured in the backend manifest.** All module rows use `duration_measured_seconds: null`/not measured despite timeouts and “slow” metadata. The source catalog therefore cannot support resource-based CI selection or safe parallelization yet. No timings were produced in this audit because tests were not executed.
9. **Some tests use sleeps, but most are bounded synchronization/polling rather than fixed-delay correctness.** AST inspection found 11 direct `time.sleep()` calls in `performance_sol_scope`, `state_snapshot_performance`, `stealthsurf_provider_boundary`, `xray_debounce`, and `xray_native_readback`; additional sleeps occur inside child-process scripts such as the writer-lock holder. Examples include bounded polling in `_wait_for_job_result` (`test_xray.py:1052-1062`) and readiness loops in native readback. These sleeps serve distinct purposes and are not all defects; review each as a fake latency window, contention fixture or readiness poll. Coalescing/concurrency behavior using fixed sleeps is less deterministic than a barrier that observes the second entrant, and should be tightened where source review confirms that race.
10. **One confirmed false-positive test exists.** `backend/tests/test_apply_pipeline.py:503-511` initializes a DB, updates a VPN module row, prints every module as `DEBUG MODULE`, then ends with `assert True`. It cannot detect a regression and emits debug output; it should be removed or replaced with assertions about the intended DB state in Phase B. This is an actual test-quality defect, not an application defect.
11. **Common test setup repeats DB initialization calls.** Static AST inventory finds 672 `initialize_database()` call sites/usages across backend test source, including shared fixture and helper calls. This is a source count, not 672 executions in one run or evidence of a latency bottleneck. Preserve per-test isolation until Phase B measures actual setup cost and tests any safe reuse.
12. **Startup is not disabled by a process-level test setting.** `main.py:81-88,170` makes module-level `app = create_app()` capture the default-enabled startup flag; conftest does not set `FWROUTER_STARTUP_TASKS_ENABLED=false`. `test_modules_lifecycle.py` imports that global app and calls `TestClient(app).get/post` (`:8-9,58-60,72-74,111-113,137-139`). These are one-shot TestClient calls, not context-manager sessions; the inspected calls do not by themselves establish that ASGI lifespan ran. Thus no scheduler start is claimed from this source review. The global app remains default-enabled if any test enters it as a context manager, so make routine test startup policy explicit and keep true startup behavior in isolated startup tests.
13. **The test suite's fake adapter substitution can hide wiring errors.** TestClient tests that monkeypatch default Xray/Mihomo/dataplane adapters validate application policy and persistence but do not validate that production adapter calls receive the correct arguments. Keep contract tests for the boundary and add separate narrow native integration tests rather than weakening fakes in every unit test.

## Execution cost and performance

No timing, CPU, RAM, disk, DB initialization or artifact size measurement was performed; doing so would require test execution, which was out of scope and unsafe without a gate-specific isolation decision. The manifest's measured duration is unset for the backend rows; per-file timeout is a ceiling, not a benchmark. Therefore safe parallelization and test-cost reduction cannot yet be evidence-backed.

Source-level cost indicators:

- Autouse fixture initializes a SQLite schema for nearly every test (unless marked `no_database_autoinit`) and installs monkeypatches per case (`conftest.py:194-222`). It also waits for default job-manager idleness before each case. Measure this overhead before considering session-scoped reuse because DB isolation is part of correctness.
- Large modules may have high setup cost and make affected-suite selection coarse: `test_xray.py` is over 4,700 lines/114 tests, `test_watchdog.py` over 3,600 lines/69 tests, and `test_apply_pipeline.py` over 3,300 lines/51 tests. Those sizes are observed from source; runtime cost is unknown.
- Concurrency tests intentionally spawn subprocesses (`test_vpn_auto_writer_guard.py`, `test_xray.py` child process coverage); native Xray starts a container and performs multiple readiness polls and a restart. Keep such tests opt-in until hosted-runner resource envelopes and cleanup are measured.
- Fixed `/tmp/fwrouter-pytest-tmp` basetemp/cache paths in `backend/pyproject.toml:43-46` can collide between concurrent invocations using the same checkout and leave shared temporary cache state. CI should give each job/run a unique explicit basetemp/cache directory and enforce cleanup/size bounds.
- No basis exists for increasing workers or sharing DB fixtures yet. Tests that use process-global env/config/cache, global job manager, writer locks or monkeypatching should be isolated before any parallel run.
- `test_debug_db_state` is a confirmed no-op assertion; DB initialization sites are numerous but their runtime cost is unmeasured.

## Prioritized Phase B–E plan

### Phase B — Test Refactoring & Standardization

1. **P0: close harness isolation gaps first.** Ensure test state paths and env are established before test application imports; fail fixture setup if prior job workers did not become idle; centralize subprocess/network/Docker guard policy; tag exceptional native cases. Add a regression proving the Xray lock and DB cannot resolve to runtime defaults in test mode. No production code change is needed to improve test harness containment.
2. **P0: reproduce and classify the eleven historical backend IDs.** Run exact IDs only after a disposable runner/state boundary is proven. Fix incorrect fixtures/assertions only after comparing the real contract. Keep unresolved items visible; no blanket baseline suppression.
3. **P1: make per-test metadata granular for mixed suites.** Refine node overrides or split test modules by test boundary, domain, level, native requirement, network requirement and slow status. Preserve one canonical owner and explicit dependency graph.
4. **P1: standardize helper/API contracts.** Consolidate repeated app/client/DB setup only where semantics remain equal; give fixtures ownership and version contracts. Remove accidental mock defaults that silently return success; require assertions on which fake methods are called and their arguments.
5. **P2: replace only evidence-backed polling/sleeps.** Use condition/event/barrier/readiness interfaces where a real asynchronous transition is under test. Keep bounded timeout and failure diagnostics; do not replace readiness validation with fixed delays.

### Phase C — Missing Test Coverage

1. **P0: full application Xray CRUD/recovery integration.** In disposable Docker Compose, drive API create/edit/route/enable/delete through jobs, DB intents, generated config, native validation, reload/restart, exact loaded users/bindings/readback, and public export. Assert response success does not precede verified convergence; verify idempotent retry, failure, unconfirmed state and exact last-good recovery.
2. **P0: crash points and restart matrix.** Inject process/container restart between intent, candidate write, validation, apply, native readback, receipt and persistence. Verify fencing, no stale overwrite, no double apply, no orphan artifacts/processes and deterministic recovery.
3. **P1: Core/provider/Mihomo contracts in one composed flow.** Exercise provider-managed target from fixture discovery through per-entry adapter normalization, candidate eligibility, Core selection, Mihomo generated config, readback and API projection. Assert ordinary/provider paths share normalization and normal selector/Health/UI make zero provider requests.
4. **P1: negative and ambiguity acceptance.** Add deterministic timeout/5xx/429/malformed provider responses, local apply failure, lost response after possible mutation, unsupported protocol/security, native mismatch, wrong incarnation, CAS change and confirm no false success or blind mutation retry.
5. **P2: API/UI/export parity.** Add role-aware API and browser/component acceptance for current/effective state, Xray target visibility and no secret-bearing output once backend integration coverage is stable.

### Phase D — GitHub Actions CI

- Only GitHub-hosted runners; no project self-hosted runner or owned test VM.
- Push: quick L0–L1; PR: affected L0–L5 including dependency closure; main: integration/native smoke; L6 separate nightly/manual/release; L7 release gate only after a hosted-compatible isolated environment is proven.
- Use Docker Compose only for isolated application integration; explicitly provision/pin native binaries/images, test that the expected suite did not skip, deny production secrets and external network by default.
- Bound job time, CPU/RAM, output, artifacts and disk; use dependency/build caches with key/version and disk cleanup; don't parallelize DB-global/runtime-using suites until isolation evidence permits it.
- The backend manifest's “duration not measured” fields must become measured evidence before tuning runner layout. Verify public-hosted runner type and actual free-tier resource/retention limits at implementation time; no assumption from old documentation is carried as current.

### Phase E — CI Acceptance

- Obtain actual GitHub Actions run evidence for push, PR and main gate behavior; verify affected domain closure, unknown-path fail-safe behavior, repeatability and no production secret exposure.
- Report selected and expanded node counts, skip reason, baseline comparison, test coverage output, suite durations, disk, CPU/RAM peak, artifacts and cleanup.
- Show L6/L7 remain separate and L7 does not run or claim staging acceptance when the hosted environment cannot satisfy isolation/compatibility. Register unsupported scenarios and retain an explicit release/staging gate.
- Acceptance requires no unexplained new failures, no silent required-native skip, deterministic re-run for flaky cases, and auditable artifact retention. No CI implementation is claimed by this Phase A report.

## Readiness criteria for the test system

The backend portion is ready to feed GitHub Actions only when (1) test environment cannot resolve production defaults before fixture setup, (2) every test node is classified or fails closed, (3) historical failures are exact-ID reproducibly triaged, (4) native tests provision immutable artifacts and cannot silently skip required coverage, (5) full Xray application CRUD/crash/recovery/native parity passes in an isolated Compose environment, (6) performance/resource timings are recorded for candidate suites, and (7) actual hosted-run evidence demonstrates the gates. This audit meets only inventory/source-review readiness; it does not satisfy any implementation or runtime gate.

## Method and limitations

- Source commit was read from Git metadata and backend test files were statically enumerated.
- Python AST was used to enumerate test definitions, fixture parameters, decorator text, assertion expressions and helper calls. It did not import the app or execute pytest collection.
- Manifest classifications are reported as authored metadata, not independently treated as correctness proof.
- Selected high-risk source paths were read directly: shared conftest/isolation, provider mock boundary, native Mihomo validation, native Xray readback, writer guard tests and Xray job polling.
- No current `pytest --collect-only`, tests, native executable, Docker, DB, production process or API was invoked. Consequently there is no current pass count, duration, runtime behavior or production reachability claim.
- Every static test function is represented with all direct assertion expressions and referenced calls. Assertions are not mechanically proven correct; explicit semantic-quality findings in this report are limited to reviewed source evidence such as the constant-true debug test, safety boundary and native skip behavior. Remaining complex test oracles still require human review in Phase B.
