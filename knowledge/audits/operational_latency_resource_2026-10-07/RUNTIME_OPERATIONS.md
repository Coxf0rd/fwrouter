# Operational runtime, deploy, startup, and native validation measurements

Audit baseline: source HEAD `65c302454038932021f25d2900b53fd0474e9db4` (`65c3024`), 2026-10-07 UTC. This report covers installer/build/startup foundation and Mihomo/Xray generation-validation call paths. It does not claim measurements for a production service restart, routing switch, subscription refresh, runtime apply, or fixed-Xray binding mutation.

## Safety and method

- No intentional live deploy, service/container restart, selector/mode switch, database mutation, provider API call, PATCH, or runtime apply was executed. Read-only API/observation windows may overlap naturally scheduled background work; the provider counter bracket is reported separately. This does not claim the live DB had zero writes throughout the entire audit window.
- Filesystem installation used the standard installer with `--deploy` and a fresh temporary target root. The installer source was checked: `--deploy` disables host package installation, Python environment setup, systemd enable/reload, Docker network creation, and sysctl changes. Its bootstrap helper received only paths under the temporary target.
- The UI has no `package.json`, bundler config, or build script; `ui/README.md` defines it as static copy-only content. UI “build” is therefore not applicable. UI installation was measured separately from backend copy.
- Startup foundation used a fresh subprocess with the deployed Python 3.11 virtualenv and current source via `PYTHONPATH`, a fresh temporary SQLite root, `FWROUTER_STARTUP_RECOVERY_ENABLED=false`, and the DNS reconcile function replaced with a no-op. It called `bootstrap_backend()` five times, without importing/starting the ASGI lifespan, listeners, schedulers, runtime recovery, or native adapters. SQL trace stored aggregate verb counts only.
- Native validation used local, immutable image IDs with `--pull=never`, `--network none`, read-only root filesystem, read-only config bind, 1 CPU, 512 MiB memory/swap, 128 PID limit, dropped capabilities, and a 16 MiB `/tmp`. Current generated configs were copied to private temporary directories (`0700`, files `0600`); output was discarded and copies removed. No container port was published. Containers were removed after the run.
- All benchmark actions held `/tmp/fwrouter-operational-audit.lock`. Process CPU, context switches and faults used fresh-process `getrusage`; file copies also used sampled process `/proc` counters. Container CPU/memory/I/O came from its cgroup v2. Host network and physical SSD activity are not attributed here.
- One accidental invalid synthetic Mihomo fixture used the reserved proxy name `DIRECT` and was rejected; changing only the temporary fixture name yielded a passing native check. This is a fixture correction, not a product failure. The final current generated profile also passed.

## Findings and candidates only

1. **Measured resource-heavy validation:** a full current Mihomo config parse takes 844 ms end-to-end in the isolated Docker path, uses about 0.5 CPU-seconds and peaks near 99 MiB under the imposed 1-CPU/512-MiB cap. The normal unchanged-input reconcile gate skips this work. This is expected safety work on changed candidates; do not remove it without equivalent native validation evidence.
2. **Generation lock occupancy candidate:** Xray generation stages and native-validates candidates while the Xray writer guard is held. The profile’s measured Mihomo parse alone is ~456 ms after Docker startup; no concurrent lock wait was created or measured. This is an attribution/future staging question, not a confirmed user-visible bottleneck and not a proposed fix here.
3. **Bootstrap statement volume:** five isolated calls each traced 131 statements including 77 `CREATE IF NOT EXISTS` schema statements; warm calls still executed four INSERT and two UPDATE statements while DB file size stayed fixed. Source shows builtin-subject normalization/upsert executes on every bootstrap. The exact page/WAL write amplification per startup was not measured because WAL was zero after close and the DB was temporary; startup invokes this once, so benchmark repeats must not be treated as production cadence.
4. **No frontend compilation work:** static copy-only deployment is both the current contract and measured path.

## Unmeasured gates

- Full `fwrouter-api.service` restart/startup/readiness duration and its scheduler/prewarm overlap.
- Actual Mihomo/Xray restart/reload duration, controller readiness, and host/container pressure during runtime recovery.
- Changed/no-op real subscription refresh timing and DB/provider call counts; provider access was intentionally not used in this workstream.
- VPN-auto/manual/Direct/fixed-client switch end-to-end user latency, readback timing, and routing effects.
- Full Xray generation and its lock wait/hold distribution; client create/delete operation duration and small-batch behavior.
- Event loop/queue delay under real API concurrency; pressure from concurrent background timers; host load, runnable tasks, and memory during these operations.
- Production SQLite transaction/page writes, WAL peak while open, SSD physical writes, long-window storage growth, and journal retention I/O.
- No production action was used to infer that success is returned before apply/readback; job-backed Xray lifecycle explicitly reports accepted separately from terminal verified status.
