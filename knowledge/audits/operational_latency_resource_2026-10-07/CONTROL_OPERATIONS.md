# Control-plane operation measurements

Baseline: source commit `65c3024`. These measurements are isolated, production-independent microbenchmarks against a temporary SQLite database and temporary log/config paths. Provider/network, Docker/systemd, Mihomo, Xray process execution and external sockets were denied or faked. They describe Python/control-plane work only; none establishes effective runtime latency or real native apply cost. SQL counts below are aggregate across the cohort, not per request. No SQL text or parameters are recorded.

## Measurement boundaries

Fast cohorts used five repeats; retention three; JSONL/database burst one bounded batch of 100; Xray attempts three. The sampler polled the process tree at 25 ms, so shorter CPU/RSS spikes can be missed. `process_cpu_ms`, context-switch counts and process I/O are aggregate cohort observations and include harness/instrumentation overhead; they are quantized and cannot be divided into exact per-action costs. The sampled RSS delta is a cohort peak, not a durable service memory delta. `/proc/loadavg`, runnable count, PSI and host network counters are host-wide and confounded by other workloads. `write_bytes` is process-accounted I/O, not physical SSD writes/fsync attribution. Temporary SQLite/WAL sizes are explicitly identified; they are not production WAL growth.

## Resource observations

In the initial control cohorts, the sampler captured a peak sampled process-tree RSS delta of 1,544 KiB; successful Xray fake-runtime follow-up peaks were up to 2,444 KiB. Values are short-lived harness peaks at 25 ms sampling, not exact service peaks. Cohort CPU totals were quantized (for example 100 ms for five settings saves and 390 ms for the 100-event database burst) and include setup/sampling overhead, so they are only coarse observations. The small SQLite file peaked at 573,440 B and its WAL at 12,392 B during the 100-event DB burst; these were temporary files. The technical JSONL burst was 63,490 bytes of characters appended. No claim about physical SSD writes follows from these counters.

Host context during the isolated cohorts showed load average around 0.85 / 0.83 / 0.74 and runnable count sampled up to 6; PSI avg10 was low (CPU some 1.46%, IO/memory some 0%). These host-level observations are context only and cannot be attributed to FWRouter operations. Host network interface counters moved during the window and are not attributable to the isolated benchmark.

## Xray lifecycle coverage and failed fixture

The initial external-client create cohort returned terminal `failed` jobs in 47–50 ms and is preserved as a failed fixture attempt, not a successful-create measurement. A targeted follow-up captured the reason and corrected only the audit fixture; see below. The first blocker was unpatched `xray_status.DEFAULT_XRAY_ADAPTER` reaching the process runner; after redirecting status to the fake adapter, the next blocker was a host DNS selective-status probe, which was supplied as deterministic temporary evidence. With those boundaries isolated, create/edit/delete/batch completed successfully through fake runtime adapters. No client enable/disable endpoint was found in the Xray client router. Native Xray validation/readback and real effective routing remain unmeasured.

## Call-chain attribution and semantics

- **Settings save:** request validation/normalization and external-connection read → settings write/commit → in-memory probe-cache clear → asynchronous read-model prewarm dispatch. The benchmark replaced prewarm with a counter/no-op; the ~10 ms result excludes background work and user-visible completion of prewarm.
- **Auto membership:** validate target and policy → acquire Xray writer guard/revalidate pool → persist configured membership and audit → conditional Core reconcile only if effective pool signature changed. The test used a temporary canonical state and mocked reconcile/selector boundary. It confirmed ordinary Auto remains editable under exclusive Provider intent without provider API work; this is a non-issue, not a performance fix.
- **Provider auto-switch policy:** validate source/subscription and read binding → guarded setting + audit persistence. The tested path does not start discovery or provider calls. The measured cohort had four changed updates and one no-op.
- **Job:** create admission and stale-job cleanup → insert job → run transition → no-op handler → terminal update/read. The observed ~49 ms p50 is bookkeeping-only; `run_now` waits for the terminal no-op in this fixture.
- **Operational event:** sanitize/normalize → DB insert/readback/commit → JSONL append. A 100-event burst performs 100 commits and 100 JSONL appends; ~443 ms in one isolated run. This establishes a serialized-work candidate for future measured review, not a production bottleneck or a fix recommendation by itself.
- **Retention:** current measured operational/technical retention calls were no-ops and did not rewrite JSONL. A seeded expired-row rewrite cohort was prepared in the benchmark script after the captured JSON was produced but was not run; rewrite cost is therefore unknown.
- **Traffic history cleanup:** select/transaction/delete/commit; one expired fixture row was deleted on first invocation and subsequent calls were no-ops. Runtime maintenance probes were not enabled.
- **Xray private route:** the measured service path persists intent only; runtime materialization/apply was outside this benchmark. No conclusion about other route paths.

## Coverage gaps / findings

No application optimization is justified by these isolated cohorts alone. The DB+JSONL burst took 442.6 ms total for 100 writes (4.43 ms/event); the single-event p50 was 3.90 ms, so the burst per-event average was about 1.14× the single-event median, not 34×. A separate technical JSONL-only 100-line append took 12.9 ms total; comparing the two batch totals gives about 34.4×, but this combines different work and is not a per-event comparison. The burst commits once per event and wrote a 73 KB temporary JSONL file; one run is insufficient to label this a production bottleneck. Settings prewarm completion, actual Mihomo/Xray apply/readback, fixed-route effective latency, physical SSD/fsync, and production queue/lock contention remain unmeasured in this sub-audit. Refer to `REPORT.md` and `LIVE_GET_RESOURCE.json` for parent-owned live/API measurements; their provider metric extraction was empty and must not be construed as zero. A separate bounded provider-counter bracket recorded no change during its own interval; it is not a whole-window/lifetime zero claim.

## Xray lifecycle follow-up

A separate bounded run corrected the audit harness without changing application code. The first failure was reproduced exactly: preflight Xray health used `xray_status.DEFAULT_XRAY_ADAPTER`, which the existing test helper had not patched; the external-command guard stopped the call in `_get_xray_status_uncached → health → _run → _default_runner`. A second host-probe boundary was explicitly replaced with a deterministic isolated DNS-contract fixture; no external process or socket was allowed. These are fixture boundaries only and make no claim about native Xray health.

Under that harness, three client-create jobs completed successfully, one alias edit returned HTTP 200/ok, and all three delete jobs completed successfully; final fixture client count was zero. The three create operation wall times were 286.9, 279.1 and 260.6 ms; deletes were 272.6, 262.5 and 264.1 ms; alias edit was 15.4 ms. Create/delete values include API request plus polling to terminal job status; the request-accepted response split from terminal completion was not retained. SQL statement counts were not instrumented in this follow-up. The lifecycle issued 12 fake Xray reloads: source paths for each no-email create call `RealXrayAdapter.create_client` (candidate `test_config` + reload) and then `materialize_xray_runtime_bindings`; each delete calls `RealXrayAdapter.delete_client` and then `materialize_xray_runtime_bindings`. Three creates plus three deletes therefore account for two fake `test_config`/reload pairs each. Alias edit only updates FWRouter metadata in `RealXrayAdapter.update_client_alias`, consistent with no additional reload. This aggregate count matches the traced source sequence; per-action counter snapshots were not captured, so that attribution is source-based rather than per-operation instrumentation. These are fake adapter actions, not native validation/runtime/readback latency. Sampled process-tree CPU, I/O and RSS are reported per operation in `XRAY_LIFECYCLE_PROBE.json`, but include instrumentation overhead and 25 ms sampling limitations. The no-op observer calibration actually took 51.904, 44.810 and 35.895 ms wall, with quantized 30, 30 and 20 ms process CPU and zero sampled RSS delta. That overhead makes CPU/RSS attribution unreliable and may add load to timing; the ~260–287 ms lifecycle values are still sampler-instrumented.

The lifecycle probe recorded source commit `65c302454038932021f25d2900b53fd0474e9db4`, fixture hash `2d5de90ba0a4724a8e33520f447ec90c60d108b296b15f45a8450a857379e7dd`, and the executed probe script hash in its evidence JSON. Client identifiers are hashed/redacted in the durable artifact. No external enable/disable endpoint exists in the Xray client router; the measured alias endpoint is the supported direct edit. The intent-only route benchmark above remains separate from applied runtime routing.
