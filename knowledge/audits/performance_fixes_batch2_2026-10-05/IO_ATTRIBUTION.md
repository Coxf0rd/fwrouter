# Stage 4B batch 2 — WAL, background overlap, and provider request evidence

Date: 2026-10-05. Source baseline under review: `1397f50cccbc768fad9fa24fc80f7bacbe820e76`. This is a bounded read-only live sample and source-owner attribution; it does not establish a long-window SSD rate or fully identify every writer.

## Boundary and method

The API was already running as PID `1686088` (started 2026-10-05 16:02:18 +07). Its runtime environment was checked by reading only the allowlisted state-directory override names; the resolved database path was `/var/lib/fwrouter-v2/fwrouter.db`, matching the sampled main DB. A 120-second passive sample ran at 10-second intervals (`n=13`), reading `/proc/<pid>/io`, RSS/CPU ticks, open SQLite database holders, and database/WAL/SHM file sizes. The script retains only numeric process/file counters, PID/comm for processes with an open database descriptor, and timestamps. `/proc/<pid>/io` is PID accounting and may include child-accounting effects; it does not identify the individual issuing thread or file. No production DB contents, credentials, configs, response bodies, or log details were collected. No service, DB, provider, or runtime state was changed.

Four serialized ordinary GETs were made on that same API process: `/servers?limit=1000&inventory_state=active&include_provider_legacy=false`, `/selector/vpn-auto?check_on_demand=false&update_ping_state=false`, `/ui/router-summary`, and `/health`. The selector request explicitly disabled on-demand checks and ping-state updates. `/health` uses the cached schema inspection path. All returned HTTP 200. Provider metrics were read through the existing local projection before/after the first three requests and around `/health`; no external provider API path was called by this measurement.

Raw sanitized counters and collection script: [live_sample_sanitized.json](live_sample_sanitized.json), [sample_live_io.py](sample_live_io.py). The measured normal GET summaries are recorded below; response payload contents were discarded in memory after byte counting.

## Attribution and disposition

The API PID accounting showed substantial write I/O while the main DB size was nearly flat and no WAL sidecar was visible at sample boundaries. That proves PID-associated I/O activity, but leaves the destination and issuing operation unknown. The interval included routine background lanes, the four recorded GETs, and potentially uncontrolled UI/CDP or other client polling; there is no basis to call it idle. No query-count, system-call path, per-thread, per-file, cgroup-device, or physical-device counter was collected. The observed cancelled-write counter is compatible with temporary-file churn, but does not prove that the existing dataplane status check caused it. Do not convert this short interval to a daily SSD estimate.

At source baseline `1397f50`, `dataplane_status._runtime_check_paths()` passes `applied.nft` to the existing `dataplane-check.sh` when an applied manifest exists. That script creates a temporary check input with `mktemp`, writes the table-delete directive plus `applied.nft`, runs `nft -c`, and removes the temporary file. The candidate change returns the applied manifest without an input file, skipping repeated candidate validation while preserving downstream live-table and applied-marker checks. This is a plausible bounded source-level explanation for avoidable temporary I/O on cache misses. The production `/proc` sample does **not** attribute any measured byte to that path. An isolated before/after reproduction measured a 490,844-byte validation input and 515 ms median for the baseline validation (`n=3`); see the batch 2 latency evidence for its exact method and limits. This isolated measurement does not allocate any part of the live process-I/O delta to that path.

The normal GET window produced zero observed provider API requests on the same API process. This is a quantitative bounded claim; it does not infer zero from absent events or logs. No unconditional provider refresh, discovery, ping, watchdog check, or external probe was invoked.

No additional write suppression is proposed from this evidence. Preserve traffic freshness, timestamps, health/recovery events, and observation semantics. A no-op UPSERT optimization would need an isolated reproduction proving identical persistent intent and timestamp/event contract before it could be proposed. The interval's single 4 KiB DB growth step and unavailable WAL-owner attribution do not yet justify that change.

## Remaining evidence gate

For the approved dataplane status optimization, capture API and owned child-process I/O around the same status-check operation on isolated existing fixtures, and compare candidate validation subprocess count, wall/CPU time, and temp-file bytes before/after. In live acceptance, use the same normal GET sequence and same-process provider metrics bracket, then report process-level I/O separately from DB/WAL size and from device counters. Keep background writer ownership open unless a measured event or isolated reproduction identifies it.
