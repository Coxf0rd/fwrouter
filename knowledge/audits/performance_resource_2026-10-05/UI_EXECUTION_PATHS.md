## Execution paths

### Admin initial view

`navigation to Admin -> one-time admin.js wire -> {loadAutolist(liveMeasure:false), loadAdminVpnOverview, loadSelectiveDefault, loadAdminDevices(false)} -> parallel endpoint/cache reads -> independent render paths` (`admin.js:1724-1732`). `loadAutolist` requests server inventory, autolist history ping data, and settings workspace (`admin.js:780-801`); the history path uses the same normalized server options as autolist, so the shared DataStore key can coalesce/cache that overlap. This is a confirmed duplicate *call path* but not evidence of duplicate HTTP work (`fwrouter-common.js:343-353,376-385`).

`loadAdminDevices` concurrently loads display settings and six role-specific inventory slices (`admin.js:1118-1130`), then combines/maps them into `adminDevicesData` and `adminVlessClients` and renders (`1131-1203`). These role slices are separate useful datasets, not duplicate calls. All six are requested before an operator selects a tab; whether deferring nonvisible roles improves usability depends on measured hidden-tab demand and whether server response semantics allow partial rendering.

Admin return-to-view refresh calls overview, selective-default, and devices together (`admin.js:1217-1242`). Summary reads may overlap each other and the shared summary refresh; ordinary reads coalesce while cached/in-flight, but forced reads do not. Locale refresh rerenders autolist and device data from existing state (`admin.js:1750-1759`), not a refetch.

### Settings initial view and inventory

`navigation to Settings -> one-time wire -> loadSettingsWorkspace + currently selected tab loader` (`settings.js:4348-4360`). Workspace completion launches `loadSettingsInventory({background:true})` without awaiting it, and controls additionally awaits proxy-server data (`1945-1972`). Initial controls boot can therefore have inventory and proxy reads concurrently; selected logs/rules/diagnostics likewise start alongside workspace.

For inventory: `domain-tab selection -> map to role(s) -> Promise.all(getSettingsInventory(role,...)) -> flatten all results -> render` (`settings.js:1894-1924`). The DataStore key includes the normalized query, role, limit, inactive flag, and live-observation flag (`fwrouter-common.js:355-364,405-414`), so a role or observation mode change correctly creates a different entry. In the `all` category, the mapped role set is broad by design; scoped categories use the role mapping in `settings.js` around `inventoryRolesForDomainTab`. Cached per-tab payloads are retained in a finite Map (one entry per visited category) and the shared DataStore retains entries keyed by query; source alone does not establish an unbounded leak.

Normal Settings inventory requests default `live_observations` to false; when placeholder health evidence is present the client starts explicit `force:true, live_observations:true` hydration (`settings.js:1895-1907,1921-1923`, hydration helper around 1830-1862). That second phase is conditionally admitted, not unconditional. Connections returns locally without API work (`1879-1883`); two click bindings reach the same connections branch, causing redundant local dispatch/render only, not duplicate network work (direct binding `4112-4119`; delegated handler nearby).

Potential admission gap: workspace always starts background inventory even when the current page tab may not need it, while the page also starts the selected tab's loader. Cache/promise paths may collapse same-category requests; this is suspected overfetch, not confirmed duplicate HTTP. Capture a cold boot request trace by tab before changing it.

### User initial view and return refresh

`navigation to User -> one-time wire -> Promise.all(loadRouting, loadServersBasic)` (`user.js:1298-1403`). Server load uses active inventory (shared cache TTL 8s), filters candidates, populates both pickers, then awaits user override and paints topology-derived ping data (`852-897`). `loadRouting` and override can both need router summary/whoami; normal DataStore reads have 2s and 3s TTL/single-flight. Initial selection does not request a manual probe; probe is a distinct explicit button action (`829-845,1390-1397`).

Return/focus/pageshow/visible handling requires User view, visible document, no pending control, no in-flight return refresh, and a 2s local minimum; then it awaits routing and override together (`1271-1295`). This is event-driven, not a 2s polling timer. Each flow can request summary; ordinary DataStore callers coalesce, while shared timer uses forced requests (below).

### Shared summary and DataStore gates

A visible user/admin/settings view starts a forced router-summary request on view change and every 15s; focus/pageshow/visibility may also trigger it (`fwrouter-common.js:7-49`). Module-level `routerSummaryRefreshPending` suppresses overlap within that shared timer path. DataStore `readCached` returns fresh payload or a pending promise only when `force` is false; `force` starts another loader and increments requestId, which prevents an older completion replacing the newer cached value but does not cancel the older request (`294-323`). Thus event-trigger overlap is bounded in ordinary paths but forced callers can bypass it; this is suspected redundant work, not a proven duplicate request rate.

TTL/key facts: whoami 3s, servers 8s, router summary 2s, workspace 8s, settings inventory/display 10s, external IP 1.5s (`fwrouter-common.js:262-270`). Expired entries are not evicted on TTL alone, but key dimensions are finite/bounded in these UI flows; do not infer a memory leak without heap/cardinality evidence. Locale changes generally rerender retained payloads; cache bypass behavior is explicit in `readCached`.

## Backend attribution boundaries

`/servers`, `/ui/settings/workspace`, and `/ui/settings/inventory` are declared synchronous FastAPI `def` handlers (`backend/fwrouter_api/routes/servers.py:116-133`; `routes/ui.py:158-175`). FastAPI runs sync endpoints in its threadpool. Parent source inspection found request-ID middleware only, with no Server-Timing breakdown. Browser wall time therefore includes queue/network/serialization/UI scheduling; it cannot by itself attribute database, helper, adapter, or event-loop cost.

The inventory helper's Health aggregation may do broader subject work than the selected role returns; this requires helper attribution and bounded role measurements before assigning the endpoint latency to Health. A live latency value observed by the parent is endpoint-level only and must not be credited solely to one helper without timings.

## Measurement plan for the next stage

Use a fresh browser context and bounded cold/warm passes for User, Admin, and Settings tabs (`all`, one scoped tab, controls, logs). Record request URL/query, start/end, status, transfer/body bytes, initiator, and whether cache/shared promise served it. Mark first usable interaction/render separately from final background completion. Capture Chrome performance long tasks and heap after each tab visit; serialize JSON-safe state cardinalities only, with secrets excluded. For backend, correlate request IDs and endpoint wall time; add temporary instrumentation only if separately approved, and distinguish threadpool queue, endpoint total, DB/helper, serialization, and response bytes. Do not infer six role calls are duplicates, or infer endpoint time is DB time. Repeat focus/visibility/locale changes to establish whether force paths actually create extra HTTP requests. No production/provider mutation is needed.

2. Measure Admin first-usable time and bytes by endpoint. If the hidden device roles dominate and are not immediately used, consider tab-scoped loading while preserving role semantics.

4. Add endpoint/helper timing only in an instrumentation-only follow-up if existing request IDs and browser timings cannot separate the relevant cost.

## Browser readiness selectors (source-verified)

Do not use wrapper child counts as loaded-row signals. The User `#serverSelect` is a picker root, and `createTablePicker()` creates trigger/menu/head/body structure before `setItems()` fills rows (`ui/index.html:71`; `ui/static/js/ping-select.js:14-40,93-139`). The Admin `#autoServerTable` likewise contains two wrapper-level sections (head/body), so root `children.length` is not server count. Use:

- **Admin server list:** `#autoServerTable [data-auto-server-row]` (`fwrouter-admin-autolist.js:269-282`). Require at least one row and absence of an explicit loading/error status; count rows separately from rows with a real `data-auto-server-row` value. The autolist is a meaningful ready signal for inventory rendering.
- **Admin device inventory:** current tab is `#adminDevicesTabLan` initially (`admin.js:70`), selected actual tab indicated by `.is-active` among `#adminDevicesTabLan`, `#adminDevicesTabExternalNetwork`, `#adminDevicesTabVless`, `#adminDevicesTabDocker`, `#adminDevicesTabHost`. Non-VLESS rows are `#adminDevicesWrap [data-admin-device-row]` (`fwrouter-admin-devices.js:290-292`); VLESS has its separate HTML renderer and rows use `#adminDevicesWrap [data-vless-client]` (`fwrouter-admin-devices.js:123-125,162-164`), so count those separately. Empty-state `.empty` is a completed empty result, not loading. Underlying load completion sets `adminDevicesLoaded=true`/`adminVlessLoaded=true` before render (`admin.js:1199-1203`).
- **User server pickers:** `#serverSelect .picklist__body [role=option][data-value]:not([data-value="__empty__"])` for VPN-auto and `#allServersSelect .picklist__body [role=option][data-value]:not([data-value="__empty__"])` for all servers. The helper emits `.picklist__row.server-table__row` (`ping-select.js:115-129`); empty inventory is represented by a synthetic `__empty__` option (`user.js:488-500,518-530`). Do not count the root `#serverSelect` as a row.
- **Settings inventory:** `#settingsClientsWrap [data-settings-client-row]` (`fwrouter-settings-inventory.js:265`) for ordinary inventory; Connections uses `[data-settings-system-row]` (`settings.js:700-703`). Inventory `items:[]` renders `.settings-events__empty`, a completed empty state (`settings.js:1555-1558`). Track pending-health rows separately with `[data-health-state="pending"]`; that means inventory rendered but live health hydration is unfinished.
- **Settings Controls:** `#settingsProxyList` begins with localized loading text in HTML (`ui/index.html:617`). Readiness should be based on its final list/empty/error state after `loadSettingsProxyServers()`, not inventory row count. Controls also include settings inventory below, which has its own readiness signal.

An aggregate `Promise.all` is not itself evidence of a product bug: it may be the intended consistency barrier for a composite render. For performance measurement, report per-request completion and first usable UI state; consider changing a barrier only if the user-visible dependency contract permits partial rendering and measurements show material delay.

## Bounded live UI evidence and matching source paths

The separate browser measurement artifact `UI_PERFORMANCE.json` (captured 2026-10-05, same source baseline) reports Settings workspace TTFB of 4.67s and 5.52s in two observed requests; Admin `/servers` TTFB 3.51s in one burst; Admin inventory TTFB 6.2s in another; Settings journal requests transferred 505,839 B and 12,238 B (decoded body bytes), respectively. By source Promise.all order, the first is the broad unfiltered recent-events request; the second is the audit-only request. Broad TTFB was 3.46s and 2.84s; audit-only TTFB was 0.56s and 2.85s. These are browser-observed endpoint timings/bytes, not backend helper timings. They establish high endpoint latency and significant journal transfer volume, but do not identify the dominant internal component.

**Settings workspace source chain:** `GET /ui/settings/workspace -> sync route -> get_ui_settings_workspace -> 2s live_probe_cache -> _build_ui_settings_workspace` (`routes/ui.py:158-160`; `services/ui_state_summary.py:141-181`). On cache miss, the builder collects display settings and broad UI workspace counts, module state, subscription metadata plus provider projection, Xray status, system-subject counts, recent operational and technical log summaries, router summary, and traffic accounting. Workspace counts traverse presence subjects and separate Xray subject rows (`services/ui_state_clients.py:465-497,579-625`). Source confirms broad composition and the cache gate; it does not show which component explains the observed 4.67/5.52s TTFB. Do not attribute those durations to inventory/Health, provider projection, Xray, SQLite, or one helper without per-stage timings.

**Settings journal source chain:** `Settings wire/tab -> loadSettingsLogs -> fetchSettingsEventsPayload -> Promise.all(GET /events/recent?limit=300&view=summary, GET /events/recent?type=audit&limit=300&view=summary) -> merge audit by event_id -> render filtered journal` (`settings.js:2205-2225,2228-2262`; `fwrouter-settings-events.js:210-227`). These are intentionally distinct query shapes: one returns all event categories, the other refreshes audit-specific records. At the backend, both sync route calls reach `list_recent_events`; the unfiltered request reads categorized operational SQLite rows and technical JSONL, while the audit-filtered request reads categorized operational rows only (`routes/events.py:122-151`; `services/events.py:1054-1101`). The audit rows from the filtered response overlap the broad response and are merged/deduplicated by ID in the browser. Thus the second request is a confirmed subset refresh/re-read for audit data, with additional network/serialization work; whether it is necessary to replace/stabilize audit records is a product contract question, so treat optimization as a follow-up candidate pending contract review. The artifact strips distinguishing query parameters from displayed route labels, but preserves request start order and byte counts; source Promise.all order supports mapping the larger first response to the broad query and the smaller second response to audit-only. Treat that mapping as source-order correlation, not a body-level inspection.

For any next optimization, add temporary stage timers around workspace subcalls and event source reads/serialization, or equivalent isolated instrumentation, only as an instrumentation-only approved step. Existing sync handlers run in FastAPI's threadpool; TTFB alone cannot separate threadpool wait, file/DB reads, helper work, JSON serialization, or response scheduling.

### Contract clarification after integration review

The extra audit-filtered journal request is intentional: the existing UI contract prevents routine events from starving the Audit tab. Overlapping row reads do not authorize deleting that request. Any payload/read optimization must retain this coverage and merge semantics. Promise.all consistency barriers and distinct role queries are confirmed source behavior, not defects by themselves. Browser request-routing overhead and cache effects are measurement limitations, not proven production root causes.
