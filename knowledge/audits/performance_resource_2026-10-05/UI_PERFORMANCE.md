# Supplementary UI performance observation

Date: 2026-10-05, Asia/Krasnoyarsk. Source baseline: `6ef940b`. This is a bounded read-only supplement to [the Stage 4 audit](REPORT.md), not a backend attribution study.

## Scope and method

Two sequential runs used the existing Chromium 153 CDP session on the same authenticated browser context and the loopback UI origin `127.0.0.1:5500`. The flow visited the User main page, Admin, the five visible Admin inventory tabs, switched locale, and opened Settings. The main page and Admin were observed in both RU and EN across the two runs. The viewport was 1440×1000. Each phase had a 20-second ceiling. The first run disabled the owned page's HTTP cache; the second reused the same browser context. Playwright route interception can bypass HTTP caching, so browser-cache reuse is unverified. Backend caches and TTLs were left untouched and naturally warmed between runs.

The harness used source-owned content markers: User picker option/current label, Admin `[data-auto-server-row]` and device row markers, and Settings event/inventory rendering. It recorded browser `PerformanceResourceTiming` request start, TTFB, download and end, request/transfer/body byte counts, CDP task/script/layout counters, long tasks, JavaScript heap and DOM counts. `pre_request_ms` is the resource-start-to-`requestStart` interval. TTFB is `requestStart` to first response byte and includes network/server waiting; it does not identify backend execution time. No API response bodies, row identities, auth storage, credentials, or unapproved query values were retained.

The route handler aborted `/api/v2/ui/external-ip` before network dispatch because that endpoint performs external fetches. It also aborted any non-GET/HEAD API request before dispatch. `/health` was not used. No refresh, ping, apply, provider workflow, database mutation, service restart, browser install, or backend cache clear occurred. The blocked external-IP attempt is excluded from network request counts and timing. Both runs recorded zero dispatched non-GET/HEAD API requests and zero rejected non-read API requests.

## Measured results

| Phase | Run 1 | Run 2 | Content signal |
|---|---:|---:|---|
| User main page | 3.40 s | 0.97 s | Current server label and one rendered picker option |
| Admin | 5.12 s | 6.73 s | 31 actual server rows; six distinct inventory roles completed |
| Settings | usable content present; observer waited to its 20 s cap | usable content present; observer waited to its 20 s cap | Event content rendered; workspace had already been fetched and cached in the Admin phase |

The Settings timeout is a harness readiness defect, not evidence that the product remained unusable for 20 seconds. That predicate required a second workspace request during the Settings phase, although the same page's Admin phase had already loaded the workspace into the UI data store. In both runs the Settings flow then requested recent events, rendered an event-list child, and loaded the `role=all` inventory. The recent-event response took 3.47 s and 2.86 s respectively; inventory responses took 4.17 s in the first run and 63 ms in the second. These response ends provide an approximate bound on data arrival, but the script did not timestamp the first visible Settings paint, so a click-to-usable Settings number is not claimed. The corrected reusable script accepts the cached workspace and checks Settings inventory markers.

The Admin inventory fan-out consisted of six distinct role queries: `lan_client`, `external_network_source`, `vless_client`, `docker_runtime`, `host_runtime`, and `router_core`. They are separate inventory slices, not duplicate same-query requests. The rendered device-tab counts were 6 LAN clients, 4 external network sources, 3 VLESS clients, 39 Docker services, and 1 host item. The Auto server table rendered 31 rows. Tab switches completed in 172–253 ms in these runs; no additional role request was observed for those tab switches.

The main-page `/servers` response was 204,001 encoded bytes and took 208 ms (run 1) and 175 ms (run 2). In run 1 it did not begin until 2.66 s after navigation; in the repeat run it began at 293 ms. This makes the cold main-page wait primarily a pre-request/startup interval in this observation, while the endpoint response itself remained near 0.2 s. The cause of that startup interval was not instrumented. Admin's `/servers` variant with provider-legacy compatibility data was 206,662 encoded bytes; it took 3.56 s in run 1 and 344 ms in run 2. Admin's `/ui/settings/workspace` was 58,467 encoded bytes and took 4.73 s and 5.59 s. The six role payloads totaled 87,311 encoded bytes per run; their timings varied substantially. In run 2, five role requests had TTFB around 5.9–6.2 s. The `router_core` request started much later than the other five: its `requestStart` was at 6.60 s after navigation (resource start approximately 1.05 s), then its TTFB was 663 ms. The resource-start-to-requestStart residual was about 5.56 s. This is a browser request scheduling/dispatch interval, not backend TTFB; Playwright routing is also part of the measurement setup, so its precise source is unproven.

Across each complete run, the browser dispatched 21 API requests (run 1) and 20 (run 2), including timed router-summary polling during the Settings observer cap. The Admin fan-out itself contains six distinct role requests, not six duplicates. Settings fetched `/events/recent` twice per run with different payload sizes: 505,839 encoded bytes and 12,238 encoded bytes. This observation alone does not establish duplicate work; the source has distinct event projections/filters and the captured query parameters were deliberately reduced. The 506 KB response is a measured payload worth preserving for a consumer/contract review. Its CPU and backend serialization cost were not measured. The OpenAPI response was 100,866 encoded bytes in each run.

## Rendering and memory evidence

CDP reported post-phase JavaScript heap snapshots of approximately 3.3–3.7 MB after User/Admin and 5.4–6.8 MB after the Settings phase's bounded observation. DOM element counts were 899 on User, 2,055 on Admin, and 6,391 on Settings. The capture's long-task maxima were 58–67 ms on User, 85–87 ms on Admin, and 140–158 ms on Settings. Script-duration deltas were 1–27 ms per User phase and 2–6 ms per Admin phase. The values are coarse renderer counters, and heap values are live snapshots without forced GC; they do not establish retained growth, a leak, or the cause of the longer page waits. No mobile viewport, external client network, host RSS, or browser memory ceiling was measured.

The measured waits align more with API/request scheduling than browser long tasks: API response TTFB and pre-request intervals accounted for seconds, while observed downloads were generally under 4 ms and recorded long tasks stayed under 160 ms. TTFB may include client-to-server transport, service queueing, backend processing, and response setup. No middleware SQL timing, serialization profile, socket queue instrumentation, or backend causal attribution was added. Therefore this audit separates the observed browser wait from rendering evidence but does not name the responsible backend component.

## Direct Settings first-load follow-up — 2026-10-05, 15:13 +07

To resolve the earlier over-strict Settings observer, one new page opened `?view=settings` directly in the existing authenticated CDP context. The page cache was disabled for this navigation. The run then changed locale from EN to RU, selected the Error journal tab, and returned to All on the same loaded page. This is a separate natural-workload window; it is not pooled with or treated as a third Admin/User run. Each wait was capped at 20 seconds. MutationObserver recorded the first source-owned event row or `.settings-events__empty` marker. The capture retained no event text or identities.

The first event-list DOM marker appeared 8.669 s after navigation, but it was an empty-or-error state with zero event rows. The pending-status key was unset at the first phase's end. Since the selector does not distinguish a legitimate empty journal from an error presentation, this marker is not counted as usable event data. An autonomous first-event-row time was not observed. Switching to Error then All rendered one and 13 actual event rows in 305 ms and 368 ms. The locale change took 314 ms, and neither it nor the two warm tab changes added an API resource. This provides a bounded warm in-document rendering measurement without claiming that the initial Settings page had usable journal rows.

The Settings workspace request remained without an observed response when the page was closed after about 9.8 s total capture time. Four of five dispatched API requests returned HTTP 200; the unanswered request was `GET /ui/settings/workspace`. The inventory remained without rendered rows, and no inventory health-pending rows were observed. Full Settings readiness is therefore unverified in this direct-load sample. This evidence explains why the earlier Admin-to-Settings capture could not assess first-load readiness: Admin had already warmed the workspace cache there, while this direct load waited on the workspace endpoint. Backend cause remains unproven.

The initial journal requests were `GET /events/recent?limit=300&view=summary` (502,974 encoded bytes; 5.890 s total, including 5.873 s TTFB and 2.6 ms download) and the audit view (5,007 encoded bytes; 1.565 s total, 1.544 s TTFB, 2.8 ms download). The Settings UI also read `/openapi.json` (100,866 encoded bytes, 34 ms total) and `/ui/router-summary` (940 bytes, 57 ms). There were five API requests in total, four completed responses, and 26 static/document requests. No external-IP attempt or non-read API request occurred.

Resource Timing recorded 2,363,634 encoded bytes across the static resources; the HTML document is not included in this sum. The largest resource was `/static/img/user-liquid-bg.png` at 1,278,996 encoded bytes, with 94 ms total resource time and 8.4 ms download. `fwrouter-i18n.js` was 231,761 bytes and `settings.js` was 199,138 bytes. CDP reported zero responses from disk cache, service worker, or prefetch cache on the page-cache-disabled navigation. The warm locale/tab changes reused in-page data; they do not establish HTTP-cache warmth. The asset sizes are a measured footprint candidate, not evidence that the image or scripts caused the event wait.

CDP JavaScript heap snapshots were 3.06 MB at the first marker and 3.58 MB after warm tab rendering; DOM counts were 482 and 578 nodes. Long-task maxima were 154 ms at the first marker and 190 ms after tab rendering. These are point-in-time renderer metrics without forced garbage collection and do not establish retained memory or a leak. No host RSS or browser memory limit was measured.
