# Database-admin backup contract

`services.database_admin.backup_database_file()` is the existing database-admin owner's snapshot primitive. Its only production-code caller is `rebuild_control_plane_database()`, reached by the separate maintenance CLI. Existing `state_retention.cleanup_state_retention()` discovers completed `backups/*.bak`; unique final names retain that contract. Retention policy is unchanged, and a receipt is not an indefinite retention pin. Private `.backup-tmp-*` orphans are not completed backups and are not newly auto-pruned. Improving the backup does **not** authorize or make a fenced rebuild eligible. Selection/routing checks, maintenance/lifecycle authority, schema compatibility and recovery prerequisites remain separate.

## Defect and qualified boundary

A raw copy of the main SQLite file can omit committed data still in WAL while remaining structurally healthy. The correction uses the [SQLite online backup API](https://www.sqlite.org/backup.html), exposed by [Python Connection.backup](https://docs.python.org/3.11/library/sqlite3.html#sqlite3.Connection.backup), rather than copying or checkpointing the source.

The source is opened read-only and an explicit read transaction is established before copying. The online copy and logical schema/data comparison refer to that **same pinned snapshot**. Commits made by another writer after the boundary are not promised to appear. This is not equality with a later live source, a global runtime transaction or proof of native generation/recovery eligibility.

Success requires SQLite integrity, foreign-key validity and content completeness, not just `integrity_check=ok`. A streamed, typed length-framed digest covers schema, cell values (including embedded NUL/BLOB), row identities and SQLite user/application version metadata; the snapshot is also reopened as standalone immutable read-only SQLite. Virtual tables and unprovable rowid layouts fail closed rather than claim generic extension support. Streaming avoids a whole-DB Python copy but memory still depends on the largest value/schema and SQLite resources. Verification must not expose row values or credentials in receipts/errors/logs. No migration, source initialization, WAL checkpoint, reconcile or source mutation is performed by this primitive. SQLite's normal read-lock/sidecar behavior is not a promise of zero host filesystem observations.

## Filesystem and failure contract

The destination is a 0600 invoking-owner file inside a unique 0700 temporary directory on the backup filesystem; the final backup directory must be owned by the invoking OS user with mode 0700. Trusted root-owned protected ancestors (and sticky root-owned temporary ancestors) are admitted, but unsafe writable ancestors are not. Unsafe path components, symlinks and untrusted permissions are rejected. Validated contents are closed into a standalone database, synchronized and published atomically without replacing an existing successful backup. File and directory synchronization complete before a success receipt. The receipt binds the actual final file and does not contain the copied rows: `backup_sha256` hashes the published bytes, `snapshot_sha256` hashes the pinned logical snapshot, and `source_snapshot=sqlite_read_transaction` identifies the boundary. Backup copying has a 30-second progress deadline and SQLite lock waits use a 30-second budget; these are not a hard deadline for arbitrary OS fsync or every validation phase.

Existing callers receive the original `ok`, `created`, `backup_path`, `db_path` result shape, with verification metadata added on creation. Missing source retains `created=false`; that does not mean a backup exists. Failure raises, preserving the rebuild caller's existing abort-before-unlink behavior. No incomplete copy is returned as a successful backup.

Cleanup is restricted to objects created by that invocation. Prior successful snapshots are not removed or overwritten. Process exceptions/interruption and publication failures do not grant permission to rebuild or restore. SIGKILL, power loss and directory-fsync uncertainty can leave a private temporary object or a complete but unacknowledged file; absence of a success receipt must not be interpreted as success. No automatic rollback, restoration or orphan pruning is introduced.

The trust boundary assumes the invoking OS owner and protected ancestors are trusted. It does not defend against a concurrent malicious root process, storage firmware lying about fsync, host loss or arbitrary out-of-band replacement of a live DB. Safe online source replacement is not implemented by this helper.

## Qualification

`backend/tests/test_database_backup.py` is a manifest-registered isolated SQLite integration suite. Existing database-admin, transfer, maintenance and selection/recovery guard suites remain relevant. Tests use only disposable synthetic databases, paths and owned child processes. They distinguish real SQLite/data checks from controlled syscall failure injection.

Ordinary test isolation forbids process spawning, so actual unprivileged-process EACCES and SIGTERM/SIGKILL process-interruption scenarios are NOT VERIFIED in this package; injected EACCES and KeyboardInterrupt are not presented as those tests. Source/CI qualification does not prove Debian host reboot/recovery, power-cut durability, actual device ENOSPC or production restore. These remain separate applicable gates; no destructive L7 or live replacement is permitted by this change. Authentication/maintenance admission findings, the Stage 5 configuration slice and private deployment wrapper are independent work.
