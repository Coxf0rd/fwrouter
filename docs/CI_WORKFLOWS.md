# FWRouter GitHub Actions CI

All automated checks use the standard `ubuntu-24.04` GitHub-hosted runner. Workflows have `contents: read`, do not use deployment credentials, and run PR code without secrets or privileged/self-hosted workers. Fork pull requests use the same test dependencies but skip writable pip caching. Checkout disables persisted credentials. Workflows use immutable action commit pins, bounded job timeouts, concurrency cancellation for stale push/PR runs, and bounded artifacts.

`push-fast.yml` is the short non-main push lane. It resolves the push event's immutable `before` commit and uses the gate manifest to select L0 plus routine affected L1 suites. L1 suites assigned to an execution profile are listed as quick-deferred; the fast report cannot be used for promotion. Main pushes use the full affected workflow instead.

`test-gates.yml` checks PR head commits against the PR event's main-base SHA and checks main pushes against the event's previous SHA. It plans the affected L0-L5 selection, runs routine suites through the safe gate coordinator, and defers profile-bound suites explicitly. Affected hosted application scenarios run with pinned Xray, Mihomo, Chromium, and Playwright inputs. The qualified-child profile covers its exact 20 native Mihomo protocol cases and six supporting process cases; the separate Docker-Xray profile covers the exact Xray readback case. These receipts bind source revision, affected-plan digest, exact IDs, runtime input hashes, and cleanup status. An aggregate report rejects missing, skipped, duplicated, wrong-source, or mismatched-profile evidence and does not promote while historical baseline failures remain unresolved.

## CI V2 artifact dependency graph

`test-gates.yml` transfers only immutable files that cross a runner boundary. The planner uploads the run/attempt-bound plan; `build` and `unit` download it, and hosted/provider/packet/native download both the plan and the verified build input. The final `affected` job downloads the exact current-run/current-attempt producer set, verifies every producer envelope and file inventory, and passes those inputs to the existing strict aggregate. Conditional profile jobs are accepted only when the immutable plan says they are selected; missing, extra, skipped, failed, cancelled, or stale-attempt evidence remains ineligible.

| Producer | Consumer | Why it crosses jobs | Internal runner-only data |
| --- | --- | --- | --- |
| `plan` | build, unit, hosted, provider, packet, native, affected | immutable affected selection, source/manifest identity, profile requirements | actionlint output and planner diagnostics |
| `build` | hosted, provider, packet, native, affected | verified backend wheel, build metadata and source-bound build summary | compiler and wheel-build temporary directories |
| `unit` | affected | complete unit report and producer envelope | pytest working tree, caches and temporary databases |
| `hosted`, `provider`, `packet`, `native` when selected | affected | pre-upload allowlisted strict receipts, exact node IDs, runtime input hashes, cleanup evidence and producer envelope | downloaded runtimes, browser, Docker/container state, resource snapshots, raw profiles, packet captures, bounded command logs and disposable state |
| strict aggregate output | final evidence publisher and failure diagnostics | aggregate eligibility, run/attempt identity, safe-recovery qualification outputs | aggregate scratch files not selected into the published bundle |

The cross-job handoff artifacts are projected to allowlisted validator inputs before upload, scoped to one workflow run and attempt, and expire after one day; no cleanup workflow or `actions: write` permission is used. Runner-only logs, resource snapshots, raw profiles, packet captures and disposable state remain on their producer runners. The aggregate validates the projected envelopes before any successful-evidence bundle can be made. A separate bounded final bundle retains selected strict-validator evidence for seven days: PR runs retain a review bundle, while only a successful `push` to `refs/heads/main` gets the name `fwrouter-main-evidence-<SHA>-<run_id>-<attempt>`. It preserves producer envelopes and their sealed handoff inventories, plus the validator inputs needed to replay strict aggregation; it omits raw logs, packet captures, separately stored profiles, raw configs and disposable state. The complete schema and trust/expiry limits are documented in [CI_ARTIFACT_LIFECYCLE.md](CI_ARTIFACT_LIFECYCLE.md). The bundle is never a substitute for the required check or proof that a bundle still exists after expiry.

Failed or incomplete runs produce a bounded diagnostic package for three days and a GitHub Job Summary when the final `affected` job runs. A workflow-wide cancellation can prevent that job from starting; then only Actions logs and the one-day producer handoffs may remain. The package records exact run identity and explicit failure/incomplete status, with redacted diagnostic projections of allowlisted JSON receipts; these projections are not original validated receipts and cannot establish qualification or claim a qualification PASS. Final publication is part of the required aggregate job, so an eligible run whose required final bundle cannot be built, verified, or uploaded fails the stable required check. No post-run deletion is needed, and no PR job receives write permissions. After handoff artifacts expire, rerun the complete workflow rather than reusing stale or incomplete evidence.

The temporary Phase D branch-validation workflow accepts exactly one commit-message marker: `ci:validate-minimal`, `ci:validate-qualified`, or `ci:validate-functional`. These stages run the focused static/bootstrap/infrastructure contracts first, then one isolated application Xray diagnostic, then qualified child and Docker-Xray profiles, and finally the complete affected L0-L5 and functional/browser cohorts. Each later stage requires the preceding stage to pass. Diagnostic and subset reports are not promotion evidence. The full affected plan is bound to fixed checkpoint `6bdf37e9c73b5728b8d50e971f34d848610eb345`, so it covers the full Phase D delta rather than only the latest incremental push. It fails closed if that checkpoint is absent from fetched history.

Main also runs one independent functional/browser acceptance pass, one qualified-child pass, and one exact Docker-Xray pass even when the changed-path plan does not require those profiles. These checks provide ongoing application and native process smoke coverage. It builds the backend wheel and syntax-checks static frontend JavaScript. It does not deploy or connect to production services.

`test-full-suite.yml` is separate from push/PR checks. It runs nightly at 04:17 UTC and can be started manually from `main` after typing `RUN L6`. The complete non-L7 manifest runs with the same hosted profile adapters and strict aggregation. L7 is excluded from L6.

`l7-recovery.yml` has only a manual trigger. It requires the `main` ref, a matching full source SHA, and the exact `RUN L7 RECOVERY` acknowledgement. It invokes only the recovery acceptance suite with the explicit recovery flag inside the isolated pinned test container. It does not invoke deployment or host reboot/system mutation.

Python packages are installed from `tests/gates/requirements-ci.txt` with hashes. Python pip cache is enabled only for trusted repository branches. Frontend sources use Node's built-in test runner and have no package manifest or dependency tree to cache. Hosted Xray/Mihomo/browser assets are downloaded once per job from pinned HTTPS assets, size-limited, and SHA-256 verified; extracted binaries, normalized Chromium bundle, and browser executable are checked against distinct pinned hashes. Docker BuildKit's runner-local layer cache can be reused within a job, while independent acceptance runs retain distinct projects, images, state, and cleanup ownership.

GitHub-hosted container runners cannot establish guest-owned systemd/PID-1, nftables dataplane, reboot, kernel-module, or host-service parity. Those host-native checks remain explicitly `NOT RUN`; process-backed Xray/Mihomo acceptance and Docker adapter checks do not substitute for them. No provider API or production endpoint is reachable from the test profile.
